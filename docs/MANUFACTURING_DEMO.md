## 启动与版本

在项目根目录复用已构建的最终镜像，不重建索引、不重放整套问答：

```powershell
$demoRelease = Get-Content -LiteralPath 'evals/manufacturing_zh_lite_v1/demo_release.json' -Raw | ConvertFrom-Json
$env:MANUFACTURING_IMAGE=$demoRelease.stable.image_id
docker compose -f compose.yaml -f compose.manufacturing.yaml up -d --no-deps --no-build api worker quality-worker
.venv/Scripts/python.exe scripts/manufacturing_workflow.py tokens --run-dir tmp/manufacturing-finalize-r1 --apply
.venv/Scripts/python.exe scripts/manufacturing_workflow.py status --run-dir tmp/manufacturing-finalize-r1
```

基础服务沿用现有Compose环境。浏览器打开`http://127.0.0.1:8000`，使用本机`tmp/manufacturing-finalize-r1/credentials.json`中的演示账号。该目录被Git忽略，凭据不要放入演示截图或报告。管理员完成复核和评测操作，普通角色用于展示可见知识库范围。16份公开原件并非企业私密生产数据。

镜像按本机已有ID启动，继续使用`--no-build`；镜像标签仅作检索说明。启动命令需要原有数据库、向量、Keycloak等基础服务就绪。上述命令只操作既有稳定版；候选镜像`enterprise-knowledge-manufacturing:timeout-868005e`独立保留，切勿把其局部补跑成绩当成稳定版的新成绩。

当前本机制造业租户已复用既有演示账号配置三个部门；账号名和密码以忽略目录`tmp/manufacturing-finalize-r1/credentials.json`为准。

| 部门 | 对应角色 | 业务知识库权限 |
| --- | --- | --- |
| 工艺部 | 工艺工程师 | 生产工艺可编辑、质量检验只读 |
| 生产部 | 操作员 | 生产工艺只读 |
| 质量部 | 质量工程师 | 质量检验可编辑、生产工艺只读 |

三个部门账号均可读公共参考库。知识管理员同时担任三个部门负责人，并保留现有三个知识库的用户级`admin`授权。部门成员通过部门继承业务库权限；负责人身份和知识库管理员权限分别维护。

这些是本机PostgreSQL运行配置，Keycloak身份仍以`sub`映射；新克隆和原初始化脚本不会自动得到这套部门关系。本机配置与接口核验记录分别位于同目录的`department-setup-report.json`和`department-http-verification.json`。原始评测的有效权限范围未改变，凭据和记录均不提交。

## 固定评分入口

对一轮已有40＋58题记录统一使用以下命令，输出目录须新建；省略`--collect-ledger`时只读本地回答，不发送HTTP请求或调用模型：

```powershell
.venv/Scripts/python.exe scripts/report_manufacturing_demo.py --run-dir tmp/某轮完整运行 --output-dir tmp/某轮完整运行/report-r13-new
```

报告入口核对发布清单中的题集、评分修订和评分程序哈希（文本按LF计算），在报告中保存发布ID与原始文件哈希。该检查只约束离线报告，不增加问答门禁；候选代码可以使用相同口径评测。修改评分口径时须另行更新发布清单并保留旧版本，不能覆盖旧成绩。

## 候选生成诊断

首轮生成请求的等待上限由60秒调至120秒，浏览器问答请求等待180秒；98题HTTP评测客户端原有180秒等待保持不变。仍为零自动重试，规划、修复等可选阶段的预算不变。三题已按预先固定名单各补跑一次，均正常返回，其中Q077仍失败；本次生成均约3秒，不能单独证明延长等待造成恢复。原始超时记录与稳定展示镜像保留。

运行包含本次改动的API后，沿现有owner快照接口`GET /api/qa/runs/{run_id}`查看`snapshot.generation.stages`：

- `answer_generation`、`answer_regeneration`或`answer_schema_recovery`保存可见首稿、claims、覆盖清单、校验错误和后处理是否改变内容；`coverage.plan_warnings`记录辅助P项问题。
- `rag_routing`保存已有计划、路由、预算及修复事件，包含`not_needed`、`ineligible`、`disabled`、`prompt_budget`等原因；`answer_decisions`保存生成及最终判定。
- `answer_completion`保存现有补全决策。诊断最多100000字节、64条事件；`generation.complete=false`表示诊断被限制或上下文未完整捕获，不能把缺失记录理解为阶段未执行。

这些内容沿用私有快照的所有者、主动共享、当前权限复核和删除规则，不加入公共问答响应，也不收集原始提示词、密钥或隐藏推理。旧快照没有这些字段，不能恢复历史首稿。新增观测本身不提高问答分数。

2026-10-30三项收敛实施阶段：问答、修复、HTTP私有快照、权限、评分与质量闭环相关438项回归通过，使用替身模型和测试数据库；对`5386a0c`原答离线重评分仍为74/98，题集、规则和原始trace哈希一致。当时未更新容器或调用模型。随后候选部署、用户98题运行与三题补跑按独立批次留存，超时调整另有110项相关回归通过，两组测试有重叠。各阶段汇总及本机产物路径见收尾记录。

## 一次约7分钟的演示

1. **资料与质量（1分钟）**：进入文档管理，选择普通PDF和一份OCR扫描件，展示原文件、分页分块、解析方式、清洗与质量标记、复核发布状态。说明“索引成功”和“可发布使用”是两个状态；OCR仍有明确限制。已发布资料直接查看，不为演示重新上传或撤回。
2. **问答与引用（1分钟）**：选择公共参考库，展示已保存的“检验报告是否必填并必须公开”问答及原文引用。核心结论为必填、是否公开由生产单位选择。需要现场新提问时，同一问题只发一次，保留实际结果。
3. **定位真实失败（1分钟）**：进入共享反馈，查找“作动器位移范围0～150mm和150～3000mm”的原问题。查看原来的拒答、请求ID、当次上下文及问题审核记录：所需原文在候选中，但未同时保留到最终上下文。原错误记录继续保留。
4. **审核样本（1分钟）**：在质量工作台查看固定样本和问题回归样本。检查参考答案、必答事实、连续原文摘录、来源版本及已审核等价表达。新版快照支撑新的回归样本，改进记录仍关联原始问题。样本获准后形成不可变的版本；资料或标注变化后须重新审核。
5. **回归与验证（2分钟）**：在“评测与改进”查看已保存的修复前、修复后两次任务。两次任务使用相同样本版本与r13评分口径，实际问答代码版本不同。逐题查看两个量程的原文、实际答案、评分、人工复核和模型用量，再查看改进记录的验证及关闭依据。演示优先读取已有任务；新建任务会产生模型调用。
6. **权限与边界（1分钟）**：切换普通角色，展示不同知识库可见范围，结合已保存的权限验收说明跨租户访问被拒绝。最后按各版本记录说明OCR、普通漏答、澄清和ERP/MES未接入等边界；候选剩余13道业务失败单列，不与稳定版历史结果混用。

## 讲述口径

- **观测**：问答具有请求ID、候选阶段、最终上下文、引用、耗时与模型调用记录，可据此区分证据遗漏和生成漏答。
- **评测**：稳定版历史84/98、候选原98题72/98及其表达复核83/98、三题恢复派生74/98及其表达复核85/98分别记录。两题闭环验证单列，三题恢复明确注明混合版本，不拼接为一次完整的新98题运行。
- **数据飞轮**：已演示“真实错误快照→共享反馈→根因审核→新回归样本→冻结版本→基线/候选实际评测→逐题复核→验证关闭”。审核由助手非独立执行，不称真实企业用户反馈或独立人工评测。
- **成本**：账本显示调用与已报告Token。没有配置单价的调用不等于免费，不报告虚构的金额成本。
- **规模**：保留原18份资料、120题及旧报告；日常演示使用16份、98题。后续增加场景应继续复用这条流程。
