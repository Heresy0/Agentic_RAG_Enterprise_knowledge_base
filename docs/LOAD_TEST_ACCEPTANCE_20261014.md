# 当前 RAG 版本压测工具与实测记录（2026-10-14）

在 `codex/rag-load-testing` 分支完善现有 Locust 工具，应用基线为 `9da810b`。不修改问答算法、权限、最终校验、RAG 预算或服务器治理配置，不新增监控组件。本轮完成两组真实正式 HTTP 测试，共 36 次 QA；修复工具误判后仅回查相同六个父块引用，没有重新发起收费 QA。

## 新增能力

- 固定 8 题负载，复用原有题集问题和可回答性标注；按简单、复杂/多跳及拒答分组，循环发出以保证样本覆盖。分组不等于实际路由。
- 支持全部授权知识库、单库自定义负载、测试前 JWT 有效期及真实 API 认证/授权预检。令牌仅在本地忽略文件与子进程环境中使用。
- 请求发出前预占额度，限制用户数、运行时间和请求总数；等待在途请求/预览结束，未完成不能记为通过。当前仅支持单进程 Locust。
- HTTP 性能、可回答性匹配和引用预览分开评分；拒答不能掩盖标注可回答问题失败，预览延迟不混入 QA P95。
- 统计规划、Agent、检索、生成、反馈、再生成、修复及校验阶段。无样本阶段保留未知，不记作零。
- 读取现有 Prometheus 计数器前后差值，观察路由、工具动作、修复、反馈、预算、终态和模型用量；这是整个 API 进程的窗口，不是逐请求路由标签。
- 停止时使用 Locust 公共接口导出最终 CSV，与逐请求记录核对数量，避免周期 CSV 漏掉尾部请求；同状态的不同端点不能覆盖彼此计数，无法合并的分位数标为未知。
- 报告不保存 JWT、问题、答案或引用正文。使用方法见 [压测指南](../tests/load/README.md)。

## 运行条件

本地 Docker API、PostgreSQL、Redis、Milvus 就绪。八个关键问答源文件与工作区按 LF 规范化后的哈希一致；父块开启、重排 top-k 为 12、输入规划与 Agent 为 auto，修复及反馈开启。共享预算保持 4 次可选模型调用、32,000 token、35 秒可选执行时间、最多 3 次检索。

每租户并发上限 3，限流为 60 次/60 秒。使用有四个知识库读取权限的 Alice，通过正式 `POST /api/qa`，覆盖 OIDC、业务授权、Redis 治理和问答链路。模型为当前部署的 `qwen3.7-flash`，嵌入及重排使用现有配置。

没有单独预热或多轮重复；本机同时运行其他进程和部分本地测试。当前数据规模为 60 份文档、516 个子块/向量、146 个父块。本轮不是隔离的容量上限实验，也不与不同负载/模型的历史结果严格比较。

## 实际结果

成功 QA 的 P95 门槛保持 15 秒；治理 429 的低延迟不计入该门槛。

| 指标 | 治理组 | 混合组 |
| --- | ---: | ---: |
| Locust 用户数 | 6 | 2 |
| QA 计划/完成数 | 12/12 | 24/24 |
| 合法 HTTP 200 | 3 | 24 |
| 并发治理 429 | 9 | 0 |
| QA HTTP 失败及 5xx | 0 | 0 |
| 成功 QA P95 | 8.824 秒 | 8.516 秒 |
| 成功 QA 最大延迟 | 8.987 秒 | 9.178 秒 |
| 可回答性匹配样本 | 3/3 | 24/24 |
| 原始组合门禁 | failed：指标窗口缺失 | failed：预览头部误判 |

混合组含简单 9 次、复杂 9 次、拒答 6 次；18 次正确接受、6 次正确拒答仅表示可回答性与原标注匹配，没有检查全部答案事实，也不是 100% 语义准确率。客户端观察 QA 吞吐约 0.318 次/秒，包含等待间隔，不能当作服务器最大 QPS。

原混合组 6 次父块预览均返回 200，但脚本把它们记作失败。修正契约后对相同六个 URL 进行独立只读回查，来源身份、文档版本、正文非空和 `Cache-Control: no-store` 全部通过，P95 约 196 毫秒，新增模型调用为 0。该回查不替代新的完整并发压测。

## 两处工具误判及处理

1. 治理组原始指标窗口缺失。诊断复现了工具对首次无样本计数器的误判：有 HELP/TYPE 声明却无数值样本时，被当成抓取失败。现在允许已声明计数器作为合法零基线；空或无关端点仍失败，重启/计数下降仍不可比较。原始采样没有保留失效原因，不能排除当时的瞬时抓取问题；治理报告保持 failed，不补造之前的指标窗口。
2. 压测脚本要求引用预览响应也有 `X-Request-ID`。实际 QA 明确返回该头部，引用预览契约只要求禁止缓存及来源校验。现在只对 QA 强制请求 ID，预览继续检查来源、版本、正文和 no-store；不修改生产 API，也不放宽原有安全校验。原始混合报告仍保持 failed，六个原链接的回查作为独立证据保存。

修正后的工具完成离线及模拟 HTTP 回归，但尚未再次运行完整的收费治理/混合场景。因此本轮可以报告 QA 性能与治理检查达标、预览回查通过，不能报告两组完整门禁已经通过。

## 路由、预算与模型用量

混合组指标窗口显示计划路由为 standard 12 次、reflective 12 次；证据收集阶段的 Agent 全部 bypassed。策略转换计数为 agentic 1 次、reflective 1 次，出现一次模型引用修复，以及一次未找到新证据的反馈补查，没有发生再生成或 Agent 决策模型调用。

可选预算为 19 次 unused、5 次 used，未观测到预算耗尽。该结果验证预算统计与普通/自检路径，不能证明 Agent 工具循环、预算耗尽、慢模型或再生成路径在压力下已经验收。

| 用量账本 | 治理组 | 混合组 | 合计 |

| 模型物理调用 | 10 | 78 | 88 |
| 已知 token | 36,723 | 280,414 | 317,137 |
| 用量未知调用 | 0 | 0 | 0 |
| 供应商错误 | 0 | 0 | 0 |

按本轮响应中的 request ID 只读核对 SQL 账本。9 次 429 没有模型调用；混合组的模型计数/token 指标差值与账本一致。缺少配置价格，因此不估算金额。接口请求上限不是模型调用次数上限。
