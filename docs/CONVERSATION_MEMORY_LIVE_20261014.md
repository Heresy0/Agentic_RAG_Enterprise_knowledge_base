# 真实模型多轮会话验证（2026-10-14）

本次结论：**三组完整场景均未通过，结构化摘要尚不能作为已完成的稳定功能。** 前置离线测试验证了程序控制和事务，但未覆盖当前真实模型与提案契约的适配问题。

使用当前 `codex/conversation-memory` 部署、`qwen3.7-flash`、Alice 的有效 Keycloak JWT 和四个授权知识库，通过真实 HTTP 创建对话、逐轮调用 `/api/qa`、读取当前用户自己的 SQL 会话诊断并删除临时对话。没有修改生产摘要规则、授权、最终校验或检索预算，也没有修改知识库文档。

共 **42/42 个 QA 请求返回 HTTP 200**，其中 **19 个 answerable=true、23 个 false**；第 7 轮起的 24 次请求中有 **21 次澄清**。HTTP 成功、可回答比例和自动关键词检查均不能当作语义准确率。

三个临时会话均通过 HTTP 删除，只清理本次创建的 ID。模型用量审计保留，原始问题、回答、状态和诊断只保存在 Git 忽略的 `data/conversation-memory/live-20261014-initial/`。可提交的安全统计见 [JSON 汇总](../evals/acceptance/conversation_memory_live_20261014.json)，公开测试题组见 [live_cases.json](../evals/conversation_memory/live_cases.json)。

## 具体问题

### 提案契约不适配真实模型

额外进行了 **3 次真实改写模型诊断**，重放三处代表性输入，只运行改写及原合并规则，不重新运行检索/生成。它们是独立复现，不是原 HTTP 请求的原始提案，不能据此断言每一轮都有相同原因。

- **条件保留，第 7 轮**：模型的排除项使用“部门负责人”作为 value，但 quote 只摘录了年份、普通员工、上海与住宿上限，value 不在 quote 内；同时还把疑问当作 claim。原规则以 `unverified memory proposal` 拒绝整份更新。
- **年份更正组，第 7 轮**：模型自行拼接 qualifier 为 `2025年/普通员工/上海/单晚`，不是原始连续片段；还提出“未知”这种不在引文中的值。首先触发 `unanchored memory qualifier`。
- **冲突组，第 8 轮**：用户仅陈述新的金额，未说明更正。模型仍建议 `replace`，原规则以 `replacement lacks explicit correction` 拒绝。这保护了旧条件，却没有保留新陈述并形成未决冲突。

这些来源和操作拒绝符合现有规则，问题是提取输出与程序契约缺少真实适配，导致正常用户会话也无法推进。不能通过放松最终校验来解决。

### 失败后缺少可靠恢复

整份提案拒绝时，有效条件也不会保存。第一次摘要建立失败后，首轮原文逐渐滑出 6 轮窗口；后续模型只能面对没有有效条件的摘要和含糊追问，形成持续重述要求。

`incomplete` 标记在后续部分有效更新后仍保持 true。冲突组第 11、12 轮已经恢复问答，状态仍处于退化标记；这会影响后续模型判断，也让自动复合检查继续失败。原始复合检查的失败不应被解释成这些恢复答案全部错误。

### 相关键选择和更正动作需要减少模型自由度

冲突组第 7 轮已经存下来源为第 1 轮的用户陈述，仍以“会话条件无法可靠确认”返回澄清。依据当前代码分支，这对应 `relevant_keys` 包含状态集合以外的键；本次 HTTP 诊断未捕获原提案，未知键的具体内容没有记录。

第 8 轮的未经更正替换被拒后，新陈述没有进入冲突状态；第 10 轮的澄清属于提案失败，不能算作已成功识别并管理冲突。后续更正能更新来源，只能证明明确更正路径有成功样例，不能证明一个已建立冲突被完整消解。

## 已表现有效的部分

- 青屿项目的初始测试金额陈述以 claim 保存，来源为第 1 轮原文；它是未经核实的用户输入，不是知识库事实。
- 不具备明确更正来源的 `replace` 被阻止，没有默默采用新金额。
- 切换到开放平台访问令牌问题时，改写没有带入青屿或两个金额，能够进行正常 RAG 问答。
- 第 11 轮明确更正后，新来源变成第 11 轮，旧来源标为 superseded，第 12 轮能回答带引用的项目准入问题，未在问题中沿用历史金额。
- 39 个会话追问各最多一次改写调用，状态没有超过项数、冲突数和字节上限；未因失败追加检索轮次或额外摘要重试。

本次未做真实撤权或并发变更测试，不能将这些观察扩展成全链路安全验证。授权和最终校验源码与前置离线验收一致。

## 后续建议

暂不把本版摘要合并为稳定功能；实际演示可先设置 `CONVERSATION_MEMORY_ENABLED=false` 并重启 API，回到已有 6 轮窗口。本次仅验证现状，没有替用户改开关。

修复应优先收敛在结构化提案适配：让模型选择有来源的字段和值，服务端负责状态键与更正/冲突动作；避免模型拼接自由 qualifier 或猜测键；补上首个摘要失败及用户完整重述后的恢复。保留权限和最终校验，先重跑这三组场景，再考虑更大评估，无需增加 Agent、检索轮次或新组件。

## 复现

检查规模而不调用模型：

```powershell
.\.venv\Scripts\python.exe scripts/run_memory_conversation_validation.py --output-dir data/conversation-memory/new-run --dry-run
```

准备有效 Alice JWT 后运行真实 API（会调用现有收费模型；必须选择新的空输出目录）：

```powershell
.\.venv\Scripts\python.exe scripts/run_memory_conversation_validation.py --output-dir data/conversation-memory/new-run --allow-model-calls
```

脚本使用现有四库权限配置，限制最多 64 轮，逐轮读取当前私有会话状态，记录真实模型阶段用量，最后删除本次创建的对话。评估脚本另有 6 项无外部调用测试，防止来源引文冒充有效状态、一般澄清冒充持久化冲突、窗口重复条件冒充长期保留或未知 token 当零计数。
